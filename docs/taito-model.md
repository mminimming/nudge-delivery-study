## 도로 전처리

`scripts/fetch_taito.py` → `scripts/build_taito.py` 순서로 수행했다. 원본은 `data/taito-osm-raw.json`, 쿼리는 `data/overpass-query.txt`, 웹용 행렬은 `data/taito-network.json`이다. 원본이 있으면 다운로드 스크립트는 재다운로드하지 않는다.

- 다운로드 경계: 남 35.692, 서 139.767, 북 35.733, 동 139.813.
- 차량 도로 등급을 선별하고 보행로·계단·고속도로 등을 제외한다. private/no 접근, 주차장 통로·driveway 등을 보수적으로 제외한다.
- 일방통행과 역방향 일방통행, roundabout 기본 방향을 처리한다.
- incoming-edge 상태를 가진 Dijkstra로 node-via 금지/지정 회전을 처리한다.
- 거점에서 왕복 가능한 도로 연결망에 건물 중심점을 연결한다. 도로 노드까지 100m를 초과하는 후보는 제외한다.
- 49개 지점(거점 1 + 기존 주문 36 + 선택 후보 12)의 방향별 경로를 산출한다. 직선거리로 배송 경로를 대체하는 fallback은 없다.
- 경로는 **가정된 기본 주행시간 최소 경로**다. 각 경로의 실제 OSM 구간 길이를 합해 거리를 기록한다.
- 원본 SHA-256, OSM snapshot 시각, seed, 속도표, 지원하지 않은 회전 관계 수를 데이터에 기록한다. 출처표시는 지도 하단에 유지한다.

한계: via-way 회전 제한, 조건부/시간대 통행 제한, 차폭·중량 제한, 차로·주차 위치·실제 건물 입구를 완전히 재현하지 않는다. 지도 경계 밖의 더 좋은 경로를 탐색하지 않는다. 도로 노드 snapping은 소규모 접근 오차를 만든다. 출입구를 확보하면 도로 edge splitting과 합법적인 정차점 지정으로 보완해야 한다.

- 다음 날 배송을 출발 전에 예약한다. 출발 뒤 추가 적재·당일 주문은 모델링하지 않는다.

- 차량 출발 09:00, 거점 복귀 마감 18:30, 대기 포함 작업시간 상한 510분.

- 기존 주문 순서는 고정하고 모든 차량·삽입 위치를 평가한다. 추가 대기 포함 작업시간 + 최대 개인시간 증가의 0.1배를 최소화한다. 동점이면 **추가** 거리를 비교한다. 이 0.1은 운영 가정이며 민감도 분석 대상이다.

정상 속도 배율: 09–11시 0.80, 11–16시 1.00, 16–18시 0.75. 혼잡 시나리오: 같은 구간에 0.55 / 0.75 / 0.50. 그 외 시간은 소스의 traffic 표에 정의했다. 기본 속도 예: primary 25km/h, secondary 22, tertiary 20, residential 14, service 10. OSM 숫자 제한속도가 더 낮으면 제한속도를 상한으로 사용한다. 신호·교차로 시간을 따로 관측하지 않았다.

## CO₂와 작업시간

기준 경로 전체를 R0, 주문을 시간창 s에 넣은 전체 경로를 Rs라 한다.

```
E(R) = Σ차량 [거리(km) / 연비(km/L) × 연료 CO₂ 계수(kg/L)]
추가 CO₂(s) = E(Rs) - E(R0)
빠른 시간대 대비 절감량 = 추가 CO₂(가장 이른 가능 창) - 추가 CO₂(s)
```

정차·공회전 연료, 에너지 생산, 창고, 차량 제조, 재배송을 포함하지 않는다. 같은 거리를 다르게 혼잡하게 달린 경우, 현재 연비법은 배출 차이를 직접 만들지 않는다. 교통은 시간창 가능성과 삽입 위치를 통해 간접적으로 영향을 준다. 전체 환경영향이나 전 과정 CO₂e로 부르지 않는다.

추가 거리가 0에 가까울 수 있다: 이미 방문할 경로의 도로 노드에 새 정차가 들어가면 운행거리가 거의 늘지 않기 때문이다. 이것은 **배송 전체 탄소가 0이라는 뜻이 아니다**. 전달 작업시간은 계속 증가한다. 모든 표시값의 원시 정밀도는 JSON에 남긴다.

```
현장시간 = 1.5분 + 건물계수 + 수령계수
         + 왕복 도로노드 접근거리 / 도보 4km/h
         + 공동주택·업무시설 계단 2분
         + 무게(kg) × 0.12분 + 부피(L) × 0.015분
건물계수: 단독 1 / 공동주택 2.5 / 업무 3분
수령계수: 문 앞 0.7 / 보관함 1 / 직접 수령 2분
```

- **activeMinutes**: 운전 + 접근·전달 작업. 참가자에게 '運転・配達の追加時間'으로 표시.
- **workMinutes**: activeMinutes + 대기. 휴식은 제외.
- **maxWorkMinutes**: 기사별 대기 포함 시간의 최댓값.

대기시간에 새 작업이 흡수되면 추가 activeMinutes는 양수이지만 추가 workMinutes는 0일 수 있다. 둘을 숨기거나 같은 의미로 표시하지 않는다. 건물 유형·엘리베이터 값은 사용자가 지정하는 시나리오이며 OSM이 확인한 건물 내부 정보가 아니다. 계단 층수·실제 하역 자세·피로도는 추정하지 않는다.

## 추천과 상태 변화

가장 이른 가능한 시간창을 비교 기준으로 삼는다. 추천은 그 창보다 (1) 운전·전달 작업, (2) 대기 포함 팀 작업시간, (3) 최대 개인시간을 모두 늘리지 않는 후보에서 추가 CO₂가 가장 적은 창이다. 최소 0.01kg의 계산상 차이가 없으면 별도 라벨을 붙이지 않는다. 이 0.01은 표시 분해능 기준이지 통계적 유의성 기준이 아니다. 환경·부담이 충돌하는 경우를 억지로 합산하지 않는다.

본 주문 화면은 참가자마다 같은 초기 상태를 부여한다. 계산 중에는 상태를 변경하지 않고 확인 단계에서만 `commit`한다. 뒤로 가서 변경하면 기존 선택·계산·확정 결과를 무효화하고 다시 계산한다. 확인을 반복해도 같은 주문이 두 번 늘어나지 않도록 주문 전 상태에서 확정 상태를 생성한다.

계산실은 연속 주문 시뮬레이션이다. 확정할 때마다 revision이 증가하고 다음 주문은 갱신된 상태에서 계산한다. 이전 revision의 결과로 예약하려 하면 거부한다. 교통 시나리오 변경은 명시적인 초기화로만 적용한다. 입력을 바꾸면 낡은 결과와 예약 버튼을 제거한다.

## 응답 저장

JSON에 입력, 상품별 가정 무게·부피 합, 계산 버전, 지도 hash, 기준 경로, 시간창별 결과·라벨, 기본선택 여부, 선택·페이지·탭 이탈 이벤트, 확정 이후 상태를 저장한다. 재노출 이력은 `exposure_history`와 `delivery_options_calculated` 이벤트에 남는다.

로컬호스트에서 설문 제출은 브라우저에만 저장한다. 계산실도 외부 전송하지 않는다. 배포된 주문 화면은 기존 Supabase 설정을 사용한다. **원격 DB에는 변경을 적용하지 않았다.** 배포 전에 `migrations/003_taito_version.sql`로 새 버전을 허용해야 한다. 기존 테이블에 행 삭제 없이 허용 버전만 확장한다. 원격 저장 검증은 아직 수행하지 않았다.

기존 `app.js`의 한국어 hash 프로토타입은 기록으로 남아 있지만 실행하지 않는다. 현재 실행 중인 `japan-app.js`는 더 이상 주소 hash로 옵션을 만들지 않는다. 기존 변경사항과 이전 로컬 저장소는 보존했다.

## 검증과 후속 보정

`node --test tests/delivery-engine.test.js`로 검증한다. 원본 데이터·행렬·계수·경로 정책을 고정하면 동일 결과를 얻는다. 검증 항목은 방향별 연결성, 36건 누락/중복, 용량, 시간창, 휴식, 단위, 입력 의존성, 추천 조건, FIFO, 불가능 입력, 예약 revision, 연속 예약의 기존 약속 유지다.

후속 우선순위:

1. 도로센서스 등으로 속도 보정, 표본 경로와 실제 소요시간 비교.
2. 실제 출입구·주차·건물별 서비스시간 확보.
3. 지역별 주문량과 시간창 수요 가정을 여러 seed·밀도로 바꿔 민감도 검토.
4. 차량 실연비·정차 연료 또는 적절한 배출 모형 확보.
5. 운영 담당자·기사 평가로 작업시간 지표의 타당성 확인.
6. 본 실험의 라벨 조건·무작위 배정·통제 시나리오 확정.

## 공유 예약 서버

로컬호스트는 브라우저 저장만 사용합니다. `experiment=<UUID>` 배포 링크는 Netlify Function과 Supabase의 `routing_experiments`, `routing_quotes`, `routing_bookings`를 사용합니다. 확정은 DB 행 잠금과 revision 비교를 거쳐 한 번만 반영됩니다. 배포 전 `migrations/004_shared_routing.sql` 실행과 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` 설정이 필요합니다. 원격 적용과 배포는 아직 실행하지 않았습니다.
